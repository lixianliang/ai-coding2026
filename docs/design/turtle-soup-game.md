# 海龟汤游戏连接设计

## 1. 目标与架构

海龟汤采用“原小智对话负责调起，独立游戏连接负责运行”的架构。原小智服务只负责理解玩家意图并调用设备工具；进入游戏后，设备的语音交互由 Go 游戏服务端独占。

```text
玩家：我要玩海龟汤
        ↓
原小智服务识别意图，调用设备 MCP 工具
        ↓
设备执行本地游戏入口
        ↓
回复 MCP：已接受启动请求，关闭原小智连接
        ↓
连接 Go 游戏服务端，请求加入指定房间
        ↓
候场、游戏问答、主持播报
        ↓
退出房间，关闭游戏连接，恢复原小智服务
```

设备配置管理游戏服务地址和认证信息。设备不根据用户传入的地址或认证信息建立连接。设备每次启动都直接申请加入指定房间，Go 游戏服务不需要提供游戏大厅。

## 2. 两套协议

| 链路 | 协议与职责 |
| --- | --- |
| 设备 ↔ 原小智服务 | 使用现有小智协议。原小智通过 MCP 调用设备本地工具，设备返回工具受理结果。 |
| 设备 ↔ Go 游戏服务 | 使用独立私有协议。控制消息可采用 JSON，音频可复用固件现有 Opus 编解码能力；协议由游戏服务定义收音、播放、禁麦、播放完成和房间状态。 |

两条连接的生命周期相互切换：游戏连接建立前使用原小智连接；游戏连接成功进入工作态后，由 Go 服务独占设备语音交互；游戏结束后关闭游戏连接，再恢复原小智服务。

## 3. 启动游戏

### 3.1 MCP 工具定义

设备提供一个普通的、可被 AI 调用的工具 `self.game.start`。该工具必须携带目标房间号，设备直接向 Go 游戏服务申请加入该房间：

```json
{
  "name": "self.game.start",
  "description": "进入指定房间开始海龟汤游戏",
  "inputSchema": {
    "type": "object",
    "properties": {
      "room_id": {
        "type": "integer",
        "description": "房间号：1、2、3",
        "minimum": 1,
        "maximum": 3
      }
    },
    "required": ["room_id"],
    "additionalProperties": false
  }
}
```

玩家说“进入 2 号房玩海龟汤”时，原小智服务下发：

```json
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "id": 1,
  "params": {
    "name": "self.game.start",
    "arguments": {
      "room_id": 2
    }
  }
}
```

设备应先向原小智服务返回受理结果：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "已接受启动请求"
      }
    ],
    "isError": false
  }
}
```

设备本地入口为：

```cpp
StartGame(int room_id);
```

### 3.2 启动时序与语义

```text
校验 room_id（只能是 1、2、3）
        ↓
立即回复 MCP：已接受启动请求
        ↓
关闭原小智连接
        ↓
连接 Go 游戏服务端
        ↓
请求加入 room_id 指定的房间
        ↓
服务端确认正式加入或进入候场状态
```

工具返回“已接受启动请求”只表示本地已经接受异步启动任务，不提前声称游戏服务已连接或已经入房。`room_id` 是申请加入的目标房间；实际归属、房间容量和候场结果由 Go 服务端校验并保存。

如果参数校验、连接或加入失败，设备提示具体原因，清理游戏连接状态，并恢复原小智服务。恢复过程应可重入，不能因为一次失败导致设备停留在无服务状态。

## 4. 游戏连接与语音交互

进入游戏大厅后，Go 服务端负责房间列表、选房、候场、游戏问答和主持播报。固件复用现有录音、Opus 编码和音频播放能力，新增游戏连接、协议消息和状态控制。

Go 服务端在一个房间内独占设备语音交互：

1. 多设备可以先上传语音。
2. Go 服务端通过 VAD 和 ASR 中间结果判断当前发言者。
3. 服务端向其他设备下发停止收音、进入收听的指令。
4. 主持播报完成后，服务端通过播放完成事件推进房间状态，再开放下一轮收音。

私有协议至少需要明确以下消息或状态：

- 设备开始、暂停和结束收音；
- 服务端下发禁麦、恢复收音和进入收听；
- 音频帧上传与 Opus 播放；
- 播放开始、播放完成及播放中断；
- 大厅、候场、游戏中、结算和离房等房间状态；
- 错误、鉴权失败、连接关闭和重连结果。

协议可以借鉴小智的 JSON 控制加 Opus 音频形式，但不继承小智现有 `listen`/`tts` 行为约束。游戏协议的状态机以 Go 服务端的房间状态为准。

## 5. 退出操作

退出操作分为“退出房间”和“退出游戏”，二者不能混用。

### 5.1 退出房间

“退出房间”只离开当前房间并回到游戏大厅，保留设备与 Go 游戏服务的连接。设备可以继续语音选房或重新加入其他房间。

建议提供无参数 MCP 工具 `self.game.leave_room`，或由游戏协议内部的离房指令触发：

```json
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "id": 2,
  "params": {
    "name": "self.game.leave_room",
    "arguments": {}
  }
}
```

处理流程：

```text
确认当前处于候场或游戏房间
        ↓
通知 Go 服务端离开当前房间
        ↓
等待服务端确认已离房
        ↓
回到游戏大厅，恢复大厅语音交互
```

服务端确认前，设备保持当前房间状态，避免本地提前进入大厅造成状态错乱。没有加入房间时执行该操作应返回“当前不在房间”，但仍保持游戏大厅连接。

### 5.2 退出游戏

“退出游戏”结束整个游戏会话：如果设备仍在房间内，先向 Go 服务端发起离房；收到确认或连接已不可恢复后关闭游戏连接，随后恢复普通小智服务。

建议提供无参数 MCP 工具 `self.game.exit`，其本地入口可对应 `ExitGame()`：

```text
退出当前房间（如有）
        ↓
关闭 Go 游戏连接
        ↓
清理游戏状态、音频和重连任务
        ↓
恢复原小智服务
```

退出游戏完成后，设备回到可被原小智服务连接的初始状态。若离房或关闭连接过程中发生网络错误，设备仍应清理本地游戏状态、提示退出结果，并恢复原小智服务。

## 6. 设备状态建议

设备至少维护以下互斥状态：

```text
XIAOZHI_CONNECTED
GAME_STARTING
GAME_LOBBY
GAME_WAITING
GAME_IN_ROOM
GAME_EXITING
```

`GAME_STARTING` 只负责异步切换，不接受重复启动；`GAME_LOBBY` 和 `GAME_IN_ROOM` 使用 Go 协议处理语音；`GAME_EXITING` 完成资源清理后只能回到 `XIAOZHI_CONNECTED`。任意启动、加入或游戏连接错误都应走统一清理路径并回到原小智服务。
