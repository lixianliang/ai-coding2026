# 海龟汤：产品定位、商业模型与评测方案

> 给桌游店、剧本杀店增加一个按包间部署的 AI 主持游戏：一台 `yunliao-s3` 放在桌上，玩家现场直接交流，需要问 AI、猜汤底或控制游戏时按 BOOT。产品不替代整名店员，而是替代“讲题、判题、公布汤底、控场”这一段可重复的主持工时。

## 1. 产品定义与边界

| 维度 | 当前产品 |
| --- | --- |
| 使用方式 | 线下多人围坐，共用一台 `yunliao-s3`；固定房间 1/2/3 |
| 音频 | 玩家之间直接听见，不经过服务端；设备只处理玩家与 AI 主持人的语音 |
| 身份 | ASR 识别说话人，按首次提问顺序显示玩家 1、2、3，无需报名字 |
| 操作 | 按 BOOT 开始收音，再按一次结束；AI 播报时设备不收麦 |
| 游戏 | 入房先欢迎，玩家说“开始游戏”后出题；猜中或超时后朗读固定汤底，再进入讨论 |
| 节奏 | 每局 10 分钟，单次提问最长 60 秒；“游戏继续”才开下一局，“退出游戏”离房 |
| 首版不做 | 多设备远程房、玩家语音转发/混音、独立声纹注册、AI 玩家、真人主持、掉线快照恢复 |

这是门店现场产品，不是远程语音社交产品。玩家本来就能面对面说话，核心价值是让包间在没有空闲主持时也能开一局，并让换场空档、夜间时段和低峰时段多一个可售项目。

## 2. 谁付费，为什么买

付费方是桌游店、剧本杀店和有独立包间的聚会门店。采购理由有两类：

1. **替代部分主持工时。** 门店仍需店员接待、开场、处理其他游戏和售后，但海龟汤的讲题、判题、公布汤底可以由设备完成。2026-10 的公开招聘样本中可见 DM 月薪约 4k–8k、兼职按场或按人头结算；这是人工成本存在的证据，不是行业均值，也不意味着本产品能替代整名员工。[招聘样本](https://m.liepin.com/s/jbsdmdylclknj2/pn4/)
2. **增加店内体验项目。** 对低端店，它是一台比专门增加晚班主持更轻量的游戏设备；对高端店，它可以成为类似 Switch、桌游架的品牌化增值项目，通过外壳、主题题库和门店 IP 做体验升级。

产品卖给门店的是“设备 + 题库 + AI 主持 + 结算页 + 运维”，不是单独卖 ASR/TTS/LLM。单店先部署一台，按包间订阅；多包间、多门店再增加设备和授权。

## 3. 成本结构：云成本低且可预测

一局只在以下节点调用云端：

- TTS：欢迎、汤面、每次短判定、冠军、固定汤底、结束提示。
- ASR：只在玩家按 BOOT 的收音区间运行，不持续听现场讨论。
- LLM：每次提问做一次短结构化判题，输出 `yes/no/close/irrelevant/correct` 和玩家名字。
- 不做连续闲聊，因此调用时长和生成量受一局 10 分钟、单次收音 60 秒的流程约束。

### 3.1 公开单价

以下为 2026-10-24 查到的公开价格，实际账单以 provider 为准：

| Provider | 当前用途 | 公开价格 |
| --- | --- | --- |
| Qwen Realtime ASR | 玩家提问转文字 | 北京区 0.00033 元/秒，即 0.0198 元/分钟 |
| MiniMax `speech-2.8-turbo` | AI 主持及固定汤底播报 | 2 元/万计费字符；1 个汉字按 2 个字符计费 |
| MiniMax `speech-2.8-hd` | 可选高音质 | 3.5 元/万计费字符；1 个汉字按 2 个字符计费 |
| DeepSeek `deepseek-flash` | 判题、提取玩家名字 | 非高峰缓存未命中输入 $0.15/百万 tokens，输出 $0.60/百万 tokens；高峰翻倍 |

以下 Qwen 成本为旧方案基线；当前豆包持续会话需计入静音保活时长，尚未核对账号实际计费，不能直接沿用下方单局估算。

来源：[Qwen ASR 定价](https://help.aliyun.com/zh/model-studio/qwen3-asr-flash-realtime)、[MiniMax 定价](https://platform.minimaxi.com/docs/pricing/overview)、[DeepSeek 定价](https://api-docs.deepseek.com/quick_start/pricing/)。

### 3.2 单局敏感性

| TTS 中文文本量 | Turbo 计费字符 | TTS 成本 |
| --- | ---: | ---: |
| 500 字 | 1,000 | 0.20 元 |
| 1,000 字 | 2,000 | 0.40 元 |
| 2,000 字 | 4,000 | 0.80 元 |

| 实际收音时长 | ASR 成本 |
| --- | ---: |
| 60 秒 | 0.0198 元 |
| 120 秒 | 0.0396 元 |
| 180 秒 | 0.0594 元 |

因此一局 TTS + ASR 约为 **0.22–0.86 元**，其中 TTS 是主要变量，但只覆盖固定播报，不随玩家长时间闲聊线性增长。LLM 按示例用量 8,000 输入 tokens、500 输出 tokens 估算，非高峰约 $0.0015/局，高峰约 $0.003/局；实际以 token 账单为准。

| 单店月开局数 | TTS + ASR 月成本 | 相对 999 元月费 |
| ---: | ---: | ---: |
| 30 局 | 6.6–25.8 元 | 低于 3% |
| 300 局 | 66–258 元 | 低于 26% |

这使门店用量增长时，云成本仍可线性预测；但“云成本低”不等于“商业模型已成立”。设备折旧、部署、内容更新、客服和售后才是需要重点验证的毛利项。

这里不包含服务器、网络、日志、设备折旧、部署和售后。早期真正可能吞掉毛利的是运维与支持，不是模型调用；这一点必须用门店试点账单验证。

计算公式：

```text
单局云成本 = ASR 单价 × 收音秒数
           + TTS 单价 × 计费字符数
           + LLM 输入/输出 tokens × 对应单价

单店月贡献 = 订阅收入 + 增量开局分成
           - 云成本 - 设备折旧 - 内容/运维/售后成本
```

## 4. 定价档位与门店回本

以下是待门店访谈验证的价格假设，不是对外报价。硬件销售/租赁费用是否并入月费也需按实际 BOM 和服务成本核算。

| 档位 | 目标门店 | 暂定月费 | 交付内容 |
| --- | --- | ---: | --- |
| Lite | 价格敏感的小店 | 499–699 元 | 1 个包间/1 台设备、标准外壳、基础题库、结算页、自助使用 |
| Standard | 普通桌游店/剧本杀店 | 999 元 | 1 个包间/1 台设备、月度题库更新、远程支持、使用报表 |
| Premium | 高端店/品牌 IP 店 | 1999 元起 | 品牌/IP 外壳、主题题库与音色、多包间管理、优先支持；多设备另计 |

按“4–6 人、人均新增 30–60 元”的示例假设，每增加一局给门店带来约 120–360 元收入；999 元月费需要约 **3–9 个增量开局/月**覆盖订阅费。这个区间只用于演示单位经济，必须用真实门店的客单价、上座率和空档时长替换。

低端店购买的是“少排一个兼职主持工时”；高端店购买的是“包间体验升级和品牌差异”。两档不能只靠硬件区分，必须靠题库更新、主题外壳、结算展示和服务响应形成差异。

## 5. 门店验证指标

| 阶段 | 指标 | 判断 |
| --- | --- | --- |
| 部署 | 首次可用时间 | 设备、Wi-Fi、Linx 入口、Game WSS 切换是否一次完成 |
| 使用 | 每店每日实际开局数 | 是否真的占用换场空档或低峰时段 |
| 完成 | 完整完成率 | ASR、判题、TTS、计时是否稳定到无需店员介入 |
| 复玩 | 说“游戏继续”的比例 | 一局结束后是否愿意继续付费/继续玩 |
| 质量 | 误判率、丢帧率、超时率、断线率 | 是否影响现场节奏和门店口碑 |
| 成本 | 单局 TTS 字符、ASR 秒数、LLM tokens | 验证模型成本是否稳定，而非只看报价 |
| 经营 | 单店月贡献、回本局数、续费率 | 验证 499/999/1999 档位是否有真实购买意愿 |

最小试点建议：3 家门店、连续 2 周，每家记录实际开局数、完成率、继续率、云用量和店员干预次数。没有这组数据前，不把任一档位写成已确认商业结论。

## 6. 评分维度与现场证据

| 评分维度 | 评委要看到 | 本方案证据 |
| --- | --- | --- |
| 商业价值 & 产品设计 50% | 谁付费、为什么持续买、单店能否回本 | 两类采购理由；Lite/Standard/Premium 三档；一台设备覆盖一个包间；TTS/ASR 单局成本敏感性；3–9 个增量开局覆盖 999 元月费的示例 |
| 架构设计 20% | 设备薄、服务端权威、协议简单 | Linx 负责入口，Go 负责游戏；复用 `hello/listen/tts` 和 Opus；不新增 waiting 状态机；玩家音频不经过设备转发 |
| AI 价值呈现 15% | AI 真正承担主持工作 | 豆包 ASR 听懂自然提问并区分说话人，DeepSeek 按固定汤底判题，MiniMax TTS 用统一音色播报；汤底由服务端锁定，模型不能改写 |
| AI 工程效率 15% | AI 产出可验证、研发经验可复用 | 模型基准 + 真实链路 E2E + 自动化测试三层验证，skills/AGENTS.md 约束执行，PR 留存证据；判题、身份、状态与音频各有明确评估函数 |

AI 研发能力的展示重点是“问题到回归”的闭环：AI 根据实际日志定位重播无响应，修复后补上延迟 stop 回归，并把排障方法写入 skill。评委可以沿着 PR 查看实现、测试和真实链路结果，而不是只看一张通过率截图。

详细指标、命令、已验证范围和待补齐能力统一见 [技术方案第 10 节](turtle-soup-game-simplified.md#10-评分维度与现场证据)。当前 8 条判题样例和合成语音回归是工程基线；真人准确率、自动 CI 和节省工时比例尚无充分数据，不作为宣传数字。

## 7. 3 分钟 Demo

| 时间 | 演示内容 |
| --- | --- |
| 0:00–0:25 | 桌游店换场空档：没有空闲主持，店主用一台设备补上一个可售项目；展示一台设备覆盖一个包间的成本结构 |

| 1:30–1:55 | 一名玩家猜中，AI 朗读冠军、固定汤底和结束提示；结算页展示本局排名 |

| 2:35–2:50 | 展示“重播没反应→回归测试→修复 PR”的证据，附提前运行的基准/E2E 结果 |

现场要证明三件事：玩家现场交流不经过设备；AI 确实完成讲题、判题和公布固定汤底；门店单位经济不依赖持续闲聊或大量云端调用。

## 8. 主要风险

- 付费意愿尚未验证。999 元/月是假设，不是市场结论；必须先做门店试点。
- “替代主持”只能替代一段流程，不能替代整名店员。接待、其他游戏、异常处理和售后仍在门店。
- 设备只服务一个包间；多包间收入必须覆盖更多设备和运维，不能按纯软件订阅估算。
- 玩家身份使用豆包 ASR 会话内聚类，短句和嘈杂环境可能误分；没有唯一编号时不计个人分。
- 门店网络与 4G 稳定性影响 ASR/TTS；网络故障时的门店兜底流程需要试点后确定。
- TTS/ASR/LLM 价格会变化；商业模型必须按实际账单每月复核，不能把当前公开价当长期承诺。
